# 03 · 策略 v2：收缩区域 + 双重定位

用户提出的新方案。取代 v0.1 计划里的"运行时数行"思路。

---

## 一、动机

### 原方案的三个痛点
1. **列表分块**（地区 → 该地区下的副本），所以才有 `structure = [2,4,7,1,9]` 这种分组表
2. **写死常量**：`total_weekly_number = 9` / `total_boss_number = 20` 已过期（实际 11/23），
   且玩家探索进度不同会导致"提前开放的区域"堆到列表头部 → **列表长度因人而异、因版本而异**
3. **用户要从上往下数到第 N 个**，数字大了人容易数错

### 新方案的两个改进
1. **利用"区域可收起"**：收起后总高度大幅缩短 → 移动距离短 → 误差小
2. **双重定位**：先选第 N 个**区域**，再选该区域下第 M 个**副本** → 用户只数小数字

---

## 二、方案要点

### 2.1 识别对象：收起箭头

- **假设**：展开态和收起态是两个不同图标，箭头方向相反
- 好处：可以靠图标区分状态，**避免重复识别/重复点击**
- 同时识别到多个箭头 → 全部拿到坐标

**已实测证实**（详见 `04-geometry.md` 第五节）：
- 展开态 = **▲**（实心正三角，尖端朝上），收起态 = **▼**（实心倒三角，尖端朝下），两者镜像
- **只识别 ▲**；▼ 不参与识别，仅在验收时作为负样本，确认 ▲ 模板不会误命中它
- 实测互斥：▲ 模板打在收起图上最高 **0.636**，打在自己状态上 0.958~1.000 → 前提成立
- 右上「索拉等级」下拉框的箭头也是 ▼，但本方案从不匹配 ▼，**不存在冲突**

### 2.2 操作顺序：从下往上收

**必须先收下面的，再收上面的**，因为收下面的块不影响上面块的位置，反之会。

规则：要收起 **N-1 个**区域，**第 N 个不收起**（留着用它下面的副本栏来选）。

若识别到 k 个箭头，N > k 时的处理需要按"收几个"推算（待细化）。

### 2.3 双重定位（新增 UI 选项）

| 参数 | 含义 |
|---|---|
| `N` | 从上往下第 N 个**区域** |
| `M` | 该区域内从上往下第 M 个**副本** |

替换原来的"从上往下第 N 个副本"。

### 2.4 适用任务（全部套同一模型）

- 无音区（TacetTask）
- 凝素领域（ForgeryTask）
- 战歌重奏（FarmEchoTask / zhange）
- 讨伐强敌（FarmEchoTask / qiangdi）
- 特异梦魇（FarmEchoTask / mengyan）

**不包含**：梦魇拔除、残像聚落（NightmareNestTask）
—— 那是"每刷完就没了、要把全部刷一遍"的策略，不走定向抓取，暂不碰。

### 2.5 特异梦魇：不保留 +5 偏移

原来 `book_serial = serial_number + 5`（跳过前 5 个巢穴）。

**新做法**：特异梦魇固定是**第 2 个区域**（它上面只有 1 个区域）。
这样即使巢穴数量随版本变化，也不用改代码。

### 2.6 状态判断：运行时记忆

- 程序自己记"已经收了几个块"
- 中途退出/异常：OKWW 自带"回主界面 → 重进 F2"，**重进即重置**，不需要持久化

### 2.7 两种情况

1. **目标已在当前页**（不用滑动）→ 直接算坐标点
2. **目标未完整出现** → 先滑再点

### 2.8 强保证

> **所有区域全部收起后，一定能在一屏内显示完**（各区域栏高度之和 < 页面高度）

所以"全部收起"是一个**已知的、稳定的基准态**，可作为计算的起点。

**已实测**（`04-geometry.md` 3.6）：收起后栏节距恒为 `0.0625 × 窗高`（1080p 下 67.5 px），
5 根栏共占约 337 px，远小于列表可视高度；且 5 根栏间距零漂移。

### 2.9 不做最后识别

**取消**最后那次 `boss_proceed` 识别，直接传坐标点击。

理由：
- 误差已大幅减小
- 便于 debug（错了就报错，不做"轮赌"式重试）
- 实际使用阶段可再加回

**建议保留的断言**：算出的坐标若落在搜索区之外，直接抛异常，而不是硬点。
这样 debug 时能立刻发现算错。

### 2.10 金色栏（限时提前开放）走不同分支

区域栏只有两类：**金色**（限时提前开放）与**普通**。

| 项 | 内容 |
|---|---|
| 判据 | 栏内取色，`G − B > 15` → 金色 |
| 实测 | 金色 `G−B = +46 ~ +47`；普通 `−8 ~ −14`；间隔 60 以上 |
| 取色区 | 栏内 `x∈[0.82,0.90]W`、栏高 30%~70% 的中位数，避开字形与辉光 |
| 分类方式 | **取色判据**，不用模板匹配（模板匹配先减均值，丢掉绝对色相） |

**流程差异**：金色区域展开后**多一个按钮需要点击，之后还要做 OCR**；普通区域没有这一步。

所以点开区域之后要先判色，再走不同分支——这是"必须区分金/黑"的唯一原因。

## 三、滚动方式：放弃滑块，改用拖拽

### 3.0 作者原本怎么滚（已核对）

**点轨道，不是拖拽，也不是滚轮。**

```python
self.click(bar_x, to_click_y)     # bar_x = 0.9730
```

在滚动条轨道上点一下，游戏自己把滑块移过去。框架虽然有 `scroll()`（发
`WM_MOUSEWHEEL`），但这个任务**没用**。

### 3.0.1 框架支持拖拽，且不占鼠标

```python
def swipe(self, from_x, from_y, to_x, to_y, duration=0.5, ...)
```

实现（`ok/device/interaction_methods/post_message.py`）：

```python
self.move(x1, y1)
self.mouse_down(x1, y1)
for i in range(steps):
    self.move(x1 + step_dx*i, y1 + step_dy*i, down_btn=MK_LBUTTON)
    self.sleep(0.01)
self.mouse_up()
```

全程走 `PostMessage` 投递 `WM_MOUSEMOVE` / `WM_LBUTTONDOWN` / `WM_LBUTTONUP`，
**不占用系统鼠标，游戏可后台**。注意 `swipe` 内含 `try_activate()`，
后台模式下可靠性需实测。

### 3.1 决定：用拖拽，不用滑块

**理由**：滑块方案要求知道"滑块位置 + 滑块长度 + 内容总高"才能算比例，
而收缩区域后这些全变；且滑块很小、下方留白少时难识别。

拖拽只需要知道**"拖多少像素"**，而双重定位让最后的 M 很小，
**拖动距离直接等于栏高度**，不需要任何比例换算。

| | 点轨道 | 拖拽 |
|---|---|---|
| 需要知道 | 滑块位置/长度、内容总高、比例 | 只要"拖多少像素" |
| 收缩后 | 比例全变，需重算 | 不受影响 |
| 误差 | 比例误差累积 | 仅一个固定映射系数 |

**遗留未知**：游戏把"拖拽 N px"映射成"内容滚动多少"？
若是 1:1 则完美；若有系数，**标定一次即可**，且与收缩无关。

### 3.2 原滑块方案的核对结果（存档）

当前 v3.7.4 `click_on_book_target` 里**没有任何滑块高度/比例的用法**（搜索为空）：

```python
bar_bottom = 0.8806      # 写死
bar_x      = 0.9730      # 写死
header_h   = 0.028       # 写死（拟合值）
container_max_rows = 4   # 写死
item_h = (bar_bottom - bar_top) / total_number   # total_number 写死 9/20
```

滑块只做了：在 `y∈[0.191, 0.271]` 窄条里找亮块取其 y，找不到 fallback `0.1963`。
**滑块长度从未测量，没有任何比例计算。**

→ 收缩区域会让原滚动计算彻底失效（内容变短但 `total_number` 不变）。
→ 反过来说明：换方案不存在"破坏原有精度"的顾虑。

### 3.3 （备选，若拖拽不可用）卷积找 bar 底边

用户思路：bar 处中间亮两边黑；bar 下方中间黑两边偏亮（背景渐白）。

不必 2D 卷积，逐行 1-D 投影即可：

```
M(y) = 中间带平均亮度  (x_c-3 .. x_c+3)
S(y) = 两侧带平均亮度  (x_c-15..x_c-8) 与 (x_c+8..x_c+15)
score(y) = M(y) - S(y)
```

从下往上扫，第一个 `score` 由负转正处 = bar 下边界。开销微秒级。

**注意**：从下往上找到的是**滑块底边**，不是轨道底边；两者只在滑块到底时重合。
若要测轨道底边，需先点轨道最底部把滑块推到底再测。

## 四、越界处理：抛错停止

作者原本行为不一致：

| 任务 | N 超出时 |
|---|---|
| `TacetTask` | `raise IndexError(f'Index out of range, max is {total_number}')` |
| `ForgeryTask` | `raise IndexError(...)` |
| `FarmEchoTask` | **不报错**，滚过去点最底行（就是 bug 来源） |

**新方案统一采用"抛错停止"**（即前两个任务的写法）：

| 情况 | 处理 |
|---|---|
| N > 识别到的区域数 | **抛错并停止** |
| M > 该区域内的副本数 | **抛错并停止** |

## 五、大区域展开后不能一屏显示（已确认）

讨伐强敌最大区域 9 项，展开后远超一屏高度。**必须保留两种情况**：

1. 目标已完整可见 → 直接点
2. 未完整可见 → 先拖拽再点

## 六、待解决：滑块 / bar_bottom（已被拖拽方案取代）

### 3.1 现状：完全没用滑块高度

当前 v3.7.4 的 `click_on_book_target` 里，**没有任何滑块高度/比例的用法**（已核对，搜索为空）。

用的是纯固定常量 + 估算：

```python
bar_bottom = 0.8806      # 写死：轨道底部
bar_x      = 0.9730      # 写死：轨道横坐标
header_h   = 0.028       # 写死：地区标题高度（拟合值）
container_max_rows = 4   # 写死：首屏放几行

bar_top = self._find_book_scroll_top()   # 只在 y∈[0.191,0.271] 找亮块取 y
                                          # 找不到 fallback 424/2160 = 0.1963

item_h  = (bar_bottom - bar_top) / total_number   # ← total_number 写死 9/20
calib_y = bar_top + item_h * serial_number
```

**结论**：
- 滑块**长度**：完全没测
- 滑块**位置**：只在顶部 86px 窄条里找，收缩后滑块移位可能直接找不到 → fallback
- **比例**：没有任何比例计算

→ **收缩区域会让原滚动计算彻底失效**（内容变短但 `total_number` 不变）。
反过来也说明：换方案不存在"破坏原有精度"的顾虑。

### 3.2 用户的卷积思路

> bar 处：中间亮、两边偏黑
> bar 下方：中间黑、两边偏亮（背景渐变变白）
> 用"中间和两边权重相反"的核，差异会非常明显

**评价：思路正确**。这是标准的"亮脊检测"（ridge / LoG 沿 x 方向）。

实现上不必做 2D 卷积，用**逐行 1-D 投影**更便宜：

```
对每一行 y：
  M(y) = 中间带平均亮度   (x_c-3 .. x_c+3)
  S(y) = 两侧带平均亮度   (x_c-15 .. x_c-8) 与 (x_c+8 .. x_c+15)
  score(y) = M(y) - S(y)

bar 区域   → score > 0
bar 下方   → score < 0
从下往上扫，第一个"由负转正"的位置 = bar 的下边界
```

开销：一次整列采样 + 一维平滑，**远小于一次模板匹配**（微秒级）。

### 3.3 一个更稳的替代：滚到底再测

如果"亮块"只有滑块（轨道本身是暗的），那从下往上扫找到的是**滑块底边**，
不是**轨道底边**，两者只有在"滑块已在最底部"时才重合。

所以可以：

1. 先点轨道最底部（`click(0.973, 0.89)`），把滑块推到底
2. 此时 **滑块底边 = 轨道底边**，直接测出来
3. 同时得到 **滑块高度**（`thumb_h`）
4. 之后再按需要滚回去

好处：`bar_bottom` 和 `thumb_h` 一次拿全，且都是实测值，不用写死。

## 八、已确认的结论

| 项 | 结论 |
|---|---|
| 滚动方式 | **拖拽**，不用滑块、不用点轨道 |
| 越界处理 | **抛错停止**（区域数或副本数超出） |
| 特异梦魇 | 固定**第 2 个区域**，不再用 `+5` 偏移 |
| 大区域展开 | 可能超一屏，**必须**保留"需滑动"分支 |
| 最后识别 | **不做**，直接传坐标；但保留"坐标越界抛异常"的断言 |
| 状态记忆 | 运行时记忆已收几个块；重进 F2 即重置 |
| 箭头识别 | **只识别 ▲**；▼ 不识别，仅作负样本验收 |
| 栏目分类 | 两类：金色 / 普通，判据 `G − B > 15`（取色，不用模板） |
| 金色分支 | 展开后多一个按钮点击 + OCR，流程与普通不同 |
